Network Automation Framework

Replacing manual, device-by-device CLI operations with a version-controlled Ansible playbook library — built around the changes the team actually makes, not the ones a framework diagram says they should.

Context: Finnish enterprise network operations; 100+ multi-vendor production devices across datacenter and edge environments.

Summary: Lead Engineer. Architected and deployed an Ansible/Python automation framework for lifecycle management and configuration changes across a fleet of 100+ multi-vendor devices. Manual touchpoints cut by 50%; multi-device changes reduced from hours of sequential CLI work to minutes of playbook runtime; high-risk changes became repeatable, auditable, zero-drift operations.

Ansible · Python IaC Multi-vendor Zero-drift

Problem

Every routine operation — configuration changes, device provisioning, software upgrades, compliance checks — was executed by hand, device by device, over the CLI. At 100+ multi-vendor devices, that meant slow change windows, inconsistent configurations that drifted apart over time, and a risk profile where the most dangerous part of any change was a human typing into a production device. The team's capacity was consumed by repetition instead of engineering.

Environment

  • Fleet of 100+ production network devices across datacenter and edge environments
  • Multi-vendor estate — no single vendor's native automation tooling could cover the fleet
  • Operations previously executed manually per device, per change, within maintenance windows

Constraints

  • Production fleet — automation had to earn trust incrementally; a bad playbook at fleet scale is a fleet-scale incident
  • Multi-vendor syntax and behaviour differences had to be abstracted without hiding what a change actually does
  • Every automated change had to remain reviewable and auditable — no opaque tooling between the engineer and the network
  • The team had to be able to run, read, and extend the framework — no single-maintainer tooling

Role and ownership

Lead Engineer: designed the framework architecture, authored the core playbook library and supporting Python tooling, and set the conventions — inventory structure, review workflow, playbook standards — that let the rest of the team contribute safely. Introduced automation to the team's operating model, not just its toolbox.

Architecture decisions

Cover the most frequent tasks first, not the most impressive ones. The library was scoped by operational frequency: configuration changes, device provisioning, and compliance checks — the work that consumed the team weekly. Ambitions like full intent-based provisioning were deliberately deferred; automating the boring 80% delivered the 50% touchpoint reduction on its own.

Git as the source of truth. Playbooks and inventory live in version control; changes are peer-reviewed before they run, and executed from a control node. Rejected: engineers running local copies — the whole value of automation collapses if two people can hold different versions of the same operation.

Ansible for orchestration, Python where Ansible bends. Ansible's inventory and idempotent module model fit fleet operations; custom Python fills the gaps — data transformation, vendor quirks, validation logic — rather than forcing everything through one tool. Rejected: a bespoke pure-Python framework, which would have been a maintenance burden only its author could carry.

Automation enforces consistency, not just speed. Playbooks are idempotent and re-runnable: applying one to an already-compliant device changes nothing, and applying it to a drifted device corrects it. This turned standby and backup configurations from a thing someone remembers to sync into a thing that cannot drift unnoticed.

Implementation

Rolled out task by task: each operation was automated, validated against a limited device set, peer-reviewed, then promoted to fleet use — building the team's trust with each cycle. Provisioning, VLAN/VRF changes, software upgrade workflows, and compliance checks moved into the library in order of operational frequency. The framework's conventions were documented in the same SOP library that governs the team's manual procedures, so automated and manual operations share one standard.

Results

  • 50% reduction in manual touchpoints across the 100+ device fleet
  • Multi-device configuration changes cut from hours of sequential CLI work to minutes of playbook runtime
  • High-risk changes became repeatable, reviewable operations with consistent results across vendors
  • Configuration drift between paired and standby systems eliminated by re-runnable, idempotent playbooks
  • Capacity shifted from repetitive execution to engineering work that scales without added headcount

Lessons learned

Adoption is the hard engineering problem. The framework only produced its numbers once the whole team ran it by default, and that took conventions, review workflow, and documentation — not more features. A playbook nobody trusts is slower than the CLI it replaces, because now the team maintains both.

Technical notes

  • Stack: Ansible playbook library with custom Python tooling for validation and vendor abstraction
  • Source control: Git-versioned playbooks and inventory; peer-reviewed changes, executed from a control node
  • Coverage: configuration changes, device provisioning, VLAN/VRF operations, multi-vendor software upgrades, compliance checks
  • Design properties: idempotent, re-runnable, auditable — drift is corrected by re-application, not detected by accident
