Nutanix HCI Migration

Transforming a legacy Cisco UCS estate into a modern Nutanix HCI platform: architecture, migration planning, network design, and service transition for 1,000+ virtual machines.

Context: Finnish enterprise platform estate; 1,000+ VMs moving from legacy blade infrastructure to hyperconverged capacity.

Summary: Technical Lead. Led the architecture and migration planning for a Cisco UCS to Nutanix HCI transformation, aligning compute, storage, network, capacity, and operational transition work so the platform could be migrated without turning the infrastructure team into the bottleneck.

Nutanix HCI Migration Virtualisation Platform Architecture

Problem

The existing Cisco UCS platform carried a large VM estate but was becoming harder to scale, operate, and refresh cleanly. The target was not a cosmetic platform swap: the migration needed a simpler capacity model, clearer operational boundaries, and a network design that would let workloads move in controlled waves.

Environment

  • Legacy Cisco UCS-based virtualization estate with 1,000+ VMs
  • Target Nutanix HCI platform integrated into existing datacenter network and operations
  • Enterprise workloads with mixed criticality, ownership, and maintenance-window constraints

Constraints

  • Migration waves had to respect application ownership, dependency groups, and service windows
  • Target capacity had to be modelled before migration, including growth headroom and failure-domain behavior
  • Network integration had to support coexistence while legacy and HCI platforms ran side by side
  • Operations needed a clear handover model: monitoring, backups, patching, and day-two ownership

Role and ownership

Technical Lead for architecture and migration planning: owned the target-state design, network integration approach, capacity model, migration sequencing, and service transition plan. Coordinated platform, network, and operations stakeholders so the migration was treated as a service move, not just a hypervisor exercise.

Architecture decisions

Capacity model before migration waves. The target HCI platform was modelled around real workload demand, failure domains, and growth headroom before migration sequencing began. This prevented the easy mistake: moving VMs first and discovering the operational limits later.

Coexistence over one-shot platform cutover. Legacy UCS and Nutanix capacity run side by side during migration. That adds temporary operational complexity, but it keeps every wave bounded, observable, and reversible.

Network design treated as part of the platform. VLANs, routing reachability, management access, and backup paths were designed with the HCI target state. The platform was not considered ready until day-two network operations had the same clarity as compute operations.

Implementation

Planned as dependency-aware migration waves: workload inventory and ownership mapping first, target capacity and network integration next, then pilot migrations before broader service groups moved. Each wave includes validation of application reachability, backup posture, monitoring, and operational ownership before the next set is approved.

Results

  • Target HCI architecture and migration approach defined for a 1,000+ VM estate
  • Legacy UCS replacement shaped around capacity, failure domains, and service transition instead of one-for-one hardware refresh
  • Network integration plan aligned with migration waves and operational handover
  • Operational model clarified for monitoring, backups, maintenance, and day-two platform ownership

Lessons learned

Platform migrations fail when they are treated as storage-and-compute-only work. The successful path is inventory, dependencies, network reachability, capacity, and operational ownership in one plan. The VM move is the visible part; the service transition around it is the architecture.

Technical notes

  • Source platform: Cisco UCS-based virtualization estate
  • Target platform: Nutanix HCI
  • Scope: architecture, capacity planning, network design, migration sequencing, and service transition
  • Execution model: pilot first, then dependency-aware migration waves with validation gates
